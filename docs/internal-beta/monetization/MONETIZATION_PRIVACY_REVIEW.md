# PromptProfit — Monetization Privacy Review

**Phase:** Internal Beta Monetization Readiness
**Date:** 2026-07-02
**Branch:** claude/windows-release-pipeline-fix-xfj0sw
**Scope:** billing/ledger events, generated monetization reports, monetization docs

---

## 1. What this review checks

That monetization events, ledger entries, and the reports generated by this
phase's tooling (`check-ledger-confidence.js`, `simulate-payouts.js`,
`check-billing-reconciliation-readiness.js`) never contain:

- prompt text
- response text
- page content
- chat history
- full URL / query string / conversation ID
- cookies / tokens
- localStorage / sessionStorage contents
- screenshots / videos / traces
- personal user data

This is enforced by a new automated gate,
`scripts/check-monetization-privacy.js` (`pnpm -w run check:monetization:privacy`),
described in section 3.

## 2. Source-level findings

### 2.1 Canonical forbidden-field list

`packages/platform-core/src/privacy-guard.ts` defines
`TELEMETRY_FORBIDDEN_FIELDS` — a single, shared list of 26 field names
(`sourceCode`, `fileContent`, `promptText`, `aiResponse`, `chatHistory`,
`pageTitle`, `pageUrl`, `pageContent`, `domText`, `clipboardContent`,
`screenshotData`, `cookieData`, `authToken`, `sessionCookie`, `apiKey`,
`secret`, `password`, `token`, and others) used by the VS Code extension,
browser extension, and API validation layer. This is the single source of
truth this review's tooling reuses (via dynamic import) rather than
re-declaring its own list, so the two can never drift.

### 2.2 What actually flows into the billing pipeline

Per `docs/internal-beta/monetization/MONETIZATION_SOURCE_AUDIT.md` (Q1-Q2)
and `docs/EVENT_LEDGER_DEDUP_REVIEW.md` §5, the only fields the extension
constructs into a billable event are: `adDecisionId`, `campaignId`,
`creativeId`, `deviceId`, `sessionId`, `extensionVersion`,
`sequenceNumber`, `clientTimestamp`, `eventId`, `adapterName`,
`displayedDurationMs`, `thresholdMs`, `renderedAt`. None of these overlap
with the forbidden list.

### 2.3 What actually flows into a ledger entry

Per `packages/ledger/src/types.ts` (`LedgerEntryInput`), a ledger entry has
exactly these keys: `entryType`, `referenceType`, `referenceId`, `account`
(`{ id, type }`), `amountMicrocents`, `description`, and an optional
`metadata`. `referenceId` is always a server-generated event/impression/
click UUID (never a ChatGPT conversation ID or page identifier — confirmed
by `ledger.service.ts`, which always passes `impressionId`/`clickId`, both
generated via `randomUUID()` on the API side, never client-supplied page
data). `description` is a fixed template string
(`"Impression charge: <id>"` / `"Click earning: <id>"`, etc.) — never
freeform or user-supplied text (`calculator.ts:44,52,60,91,99,107`).

### 2.4 What this phase's new reports contain

`LEDGER_CONFIDENCE_REPORT.md` and `PAYOUT_SIMULATION_REPORT.md` are
generated entirely from **synthetic, fixed-in-code fixtures** (see the
scripts that generate them) — synthetic IDs like
`synthetic-developer-01`, `synthetic-advertiser-alpha`, fixed test emails
like `dev01@example.test`. No real developer/advertiser identifiers, no
ChatGPT content, no page data ever enters these reports because the
scripts that generate them never read from any live event source — they
only call the pure `LedgerCalculator`/`FraudScorer` production code against
in-script fixture data.

## 3. Automated gate: `check:monetization:privacy`

`scripts/check-monetization-privacy.js` runs 6 checks:

| # | Check | Scope | Result |
|---|-------|-------|--------|
| 1 | No forbidden field used as an object/schema key | `packages/shared/src/types`, `packages/telemetry/src`, `packages/platform-core/src` (excl. privacy-guard.ts itself) | PASS |
| 2 | No forbidden field used as an object key | Browser-extension mock/fixture files, `scripts/__tests__/fixtures` | PASS |
| 2b | Exempted privacy-rejection test files genuinely test rejection (not blind-trusted) | `privacy-guard.test.ts`, `privacy.test.ts`, `event-schema.test.ts`, `chatgpt.privacy.test.ts` | PASS |
| 3 | No forbidden field as a data key in this phase's generated reports | `LEDGER_CONFIDENCE_REPORT.md`, `PAYOUT_SIMULATION_REPORT.md`, `BILLING_RECONCILIATION_REPORT.md` | PASS |
| 4 | No leaked `ppft_` API key pattern | All `docs/internal-beta/monetization/*.md` | PASS |
| 5 | Canonical forbidden-field list sanity (contains the required monetization-relevant subset) | `TELEMETRY_FORBIDDEN_FIELDS` | PASS |

Run this session:
```
$ node scripts/check-monetization-privacy.js
Passed: 6
Failed: 0
Result: PASS
```

### Why an exemption exists (and how it's validated, not just trusted)

`privacy-guard.test.ts`, `privacy.test.ts`, `event-schema.test.ts`, and
`chatgpt.privacy.test.ts` legitimately contain forbidden field names — as
**test input proving the schema/guard rejects them** (e.g.
`expect(validateBrowserEvent({ pageTitle: "My Chat" })).toMatch(/pageTitle/)`).
A naive scan flagged these as false positives on first run of this script;
rather than blanket-trusting an exemption list, check 2b re-scans every
exempted file and fails if a forbidden field appears WITHOUT the word
"reject" nearby in the same file — i.e., the exemption is itself checked,
not assumed.

## 4. Manual/table verification against the required forbidden-data list

| Forbidden data | Present in monetization pipeline? | Evidence |
|-----------------|-----------------------------------|----------|
| Prompt text | No | Not in event schema (§2.2), not in ledger entry (§2.3) |
| Response text | No | Same as above |
| Page content | No | Same as above |
| Chat history | No | Same as above |
| Full URL / query / conversation ID | No | `referenceId` is always a server-generated UUID, never client page data |
| Cookies / tokens | No | Not in event schema; service worker is a pass-through with no cookie access (`docs/EVENT_LEDGER_DEDUP_REVIEW.md` §9) |
| localStorage / sessionStorage contents | No | Not read or transmitted anywhere in the billing pipeline |
| Screenshots / videos / traces | No | Not part of the billing event or ledger pipeline at all |
| Personal user data | No | `deviceId` is a pseudonymous, extension-generated identifier not linked to email/name (`docs/EVENT_LEDGER_DEDUP_REVIEW.md` §4) |

## 5. Limitations

1. This review is static (source + generated-report scanning). It does not
   run a live network capture of real traffic — that requires a staging
   environment (**not verified yet** in this sandbox; no Docker/staging
   available).
2. The exemption mechanism (§3) is pattern-based (presence of the word
   "reject"); a determined bad actor deliberately trying to defeat the gate
   could word a real leak to include that word. This is a defense-in-depth
   check, not the sole privacy control — the primary control remains the
   closed Zod schemas (`TelemetryEventSchema`) that reject unknown fields
   at the API boundary.
3. This review covers the **monetization/billing** pipeline specifically.
   The broader browser-extension privacy posture (content-script isolation,
   DOM access boundaries) is covered separately in
   `docs/CHATGPT_BROWSER_PRIVACY_SECURITY_AUDIT.md` and
   `docs/internal-beta/PRIVACY_SECURITY_ONE_PAGER.md`, not re-audited here.

**Result: PASS.** No forbidden monetization data was found in event
schemas, mock payloads, or this phase's generated reports. The automated
gate (`check:monetization:privacy`) is wired into the verification suite
(Phase 9) and can be re-run at any time to re-confirm.
