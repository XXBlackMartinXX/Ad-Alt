## 1. Purpose and Clean-Room Declaration

This document records the publicly observable behaviors of the reference product (kickbacks.ai), establishes what Ad-Alt may not copy, and specifies the original product concept that Ad-Alt will build. This document was written from public information only (website copy, public VS Code extension manifest, public extension description, publicly stated developer program terms). No proprietary source code, internal designs, API schemas, or confidential materials were reviewed.

Engineering teams must treat this document as the authoritative line between "public-domain inspiration" and "off-limits implementation." When in doubt, stop and escalate to the legal/product lead before building.

## 2. Reference Product: Public Facts

**Label: PUBLIC FACTS — observed from public sources only**

The following is what the reference product (kickbacks.ai) publicly appears to do, based on publicly available information:

### 2.1 Developer-Side Behavior

- **Mechanism:** A VS Code extension that displays sponsored text messages during periods when an AI coding assistant is "thinking" or waiting on a response.
- **Earn model:** Developers earn approximately 50% of ad revenue generated by impressions and clicks shown in their editor.
- **Auth:** Developers authenticate via OAuth. Credentials appear to be stored in the OS keychain.
- **Opt-in:** The extension installs and presumably requires some form of account linkage before ads are shown.
- **Telemetry:** The extension reports impression and click events back to the service.
- **Killswitch:** A mechanism exists to remotely disable ad serving without requiring a new extension release.
- **AI detection:** The extension contains adapters that detect when specific AI tools (Claude Code, GitHub Copilot/Codex) are in a "thinking" or "waiting" state. This detection uses some form of editor event or API observation.

### 2.2 Advertiser-Side Behavior

- **Ad unit:** Text-only sponsored messages shown in the VS Code status bar or similar passive area during AI wait states.
- **Auction:** Advertisers purchase blocks of impressions via what is described as an English ascending auction (open-cry, highest bidder wins).
- **Click premium:** Click events are valued at 50x the impression rate, creating strong incentive for ads with clear calls to action.
- **Self-serve:** Advertisers appear to be able to purchase and manage campaigns without direct sales involvement.

### 2.3 Infrastructure (Inferred from Public Description)

- **Idempotent telemetry:** The extension appears to send idempotent event tokens so that duplicate event delivery does not double-count billable events.
- **Revenue split:** Revenue split happens server-side; developer dashboard presumably shows earnings.
- **Extension architecture:** Uses adapter pattern to support multiple AI tools without hard-coding per-tool logic.

## 3. What Ad-Alt Must NOT Copy

The following are off-limits. These are design decisions, implementations, schemas, or business logic that belong to the reference product and cannot be reproduced:

1. **Any source code** from the reference extension, backend, or web app — even if reverse-engineered.

3. **Specific prompt/heuristic text** used to detect AI thinking states if those are proprietary.
4. **The exact auction mechanism implementation** — we must design our own auction logic from first principles.
5. **The specific event token format or idempotency key algorithm** used for telemetry deduplication.

## 4. Ad-Alt Clean-Room Product Concept

Ad-Alt is a privacy-by-construction, developer-respecting monetization platform for AI wait-states in coding tools. It is built from first principles, informed by the existence and general concept of the reference product but not by any of its proprietary implementation.

### 4.1 Core Concept

When a developer is using an AI coding assistant, there are predictable idle moments while the AI generates a response. These moments — typically 5–30 seconds — are "dead time" from a developer attention standpoint. Ad-Alt converts these moments into a value exchange:

- **Developers** see a single, tasteful, brand-safe sponsored text message (a "PauseMoment") during the AI wait. They earn a share of revenue.
- **Advertisers** reach a high-value, high-intent professional audience at the exact moment of receptive availability.
- **Ad-Alt Inc.** takes a platform fee and provides the matching, serving, fraud scoring, and payment infrastructure.

The platform is built with developer trust as the primary constraint. Every design decision prioritizes transparency, consent, and privacy over revenue optimization.

### 4.2 "PauseMoment" Ad Unit

The atomic unit of Ad-Alt is the **PauseMoment**: a single sponsored text message displayed passively in the VS Code status bar during an AI-triggered wait state. It is:

- Text-only (no images, animations, or rich media)
- A maximum of 120 characters of visible copy
- Optionally includes a short URL or promo code
- Shown once per AI invocation (not repeatedly during the same wait)
- Dismissible by the developer at any time
- Never shown unless the developer has explicitly opted in

## 5. User Personas

### 5.1 Developer / Earner ("Dev")

**Who:** A professional software developer who uses AI coding assistants (Claude, Copilot, Cursor, etc.) daily. They work in VS Code (or a fork thereof). They want to earn passive income without disrupting their workflow.

**Goals:**
- Earn money during time that would otherwise be idle
- Understand exactly how much they've earned and why
- Trust that no sensitive data (code, prompts, file contents) is being sent anywhere
- Be able to stop participation at any time with full data deletion

**Frustrations:**
- Black-box earnings calculations
- Privacy-opaque extensions
- Extensions that slow down the editor or break things
- Ads that are embarrassing or off-brand for their professional context

### 5.2 Advertiser ("Adv")

**Who:** A company (typically dev tools, SaaS, or developer education) that wants to reach software developers. They have a marketing budget and want measurable ROI with a self-serve experience.

**Goals:**
- Reach a qualified developer audience efficiently
- Set a budget and not overspend
- Get attribution data for campaign optimization
- Ensure their brand is shown in a professional context

**Frustrations:**
- Unknown audience quality
- Ad fraud eating budget
- Brand safety risks (ad shown next to bad content)
- Lack of spend transparency

### 5.3 Admin / Creative Reviewer ("Admin")

**Who:** An Ad-Alt employee responsible for reviewing advertiser-submitted ad creative before it is eligible to serve.

**Goals:**
- Approve legitimate ads quickly (target: under 4 business hours)
- Reject or request revision of off-brand, misleading, or inappropriate creative
- Maintain a consistent creative quality standard
- Escalate edge cases to legal or product

**Frustrations:**
- Vague approval criteria leading to inconsistent decisions
- High volume of low-quality submissions slowing the queue
- No tooling for bulk decisions or template-based rejection reasons

### 5.4 Finance / Operator ("Finance")

**Who:** An Ad-Alt finance team member responsible for ensuring the accounting ledger is accurate, reconciling Stripe payouts, and issuing developer earnings disbursements.

**Goals:**
- Verify that every dollar in from advertisers is accounted for in the ledger
- Ensure developers are paid correctly and on schedule
- Audit any fraud adjustments or clawbacks
- Export data for tax and compliance purposes

**Frustrations:**
- Floating-point rounding errors in financial calculations
- Opaque fraud adjustments reducing payout trust
- Manual reconciliation of Stripe webhooks vs. internal ledger

## 6. Core User Stories

### Developer Stories

**DEV-01 — Explicit Opt-In**  
As a developer, I want to be shown a clear, plain-English consent screen before any ad is displayed, so I know exactly what I'm signing up for and can make an informed decision.  
*Acceptance:* No PauseMoment is served until the developer has explicitly clicked "I agree and want to participate" in the VS Code extension UI.

**DEV-02 — Earnings Visibility**  
As a developer, I want to see a real-time ledger of every PauseMoment that generated earnings for me, including the advertiser name, the timestamp, whether it was an impression or a click, and the exact amount in cents, so I can verify my payout is correct.  
*Acceptance:* The developer dashboard shows a paginated, filterable event log. Every billable event row shows all four fields.

**DEV-03 — Privacy Guarantee**  
As a developer, I want to know with certainty that the extension never sends my code, file paths, prompt contents, or any work-product to Ad-Alt servers, so I can safely use it in professional and proprietary codebases.  
*Acceptance:* The telemetry schema is published publicly and machine-readable. Extension source is open-source (MIT). An independent audit confirms no work-product data leaves the machine.

**DEV-04 — Instant Opt-Out**  
As a developer, I want to be able to disable ad serving instantly from within VS Code, without uninstalling the extension, so I can pause participation during sensitive work or demos.  
*Acceptance:* A single-click "Pause PauseMoments" command is available in the command palette and takes effect on the next AI invocation (no restart required).

**DEV-05 — Full Data Export and Deletion**  
As a developer, I want to export all data Ad-Alt holds about me in a machine-readable format and, separately, request full account deletion, so I maintain control of my data.  
*Acceptance:* Dashboard provides one-click CSV/JSON export. Deletion request is processed within 30 days and sends a confirmation email.

**DEV-06 — Stable Editor Experience**  
As a developer, I want the Ad-Alt extension to use only stable VS Code APIs so that it never breaks my editor after a VS Code update.  
*Acceptance:* Extension uses only the published VS Code Extension API. No DOM manipulation, no `eval()`, no monkey-patching. If AI state detection fails, the extension silently degrades (no ads shown, no editor errors).

### Advertiser Stories

**ADV-01 — Self-Serve Campaign Creation**  
As an advertiser, I want to create a campaign, write my ad copy, set a budget, and submit it for review without talking to a sales rep, so I can move quickly.  
*Acceptance:* Advertiser completes campaign creation in under 10 minutes from sign-up to creative submission.

**ADV-02 — Auction Participation**  
As an advertiser, I want to set a max CPM bid and have the system automatically enter me into the auction, so I win impressions competitively without manual bidding.  
*Acceptance:* Bid is honored in the ad-serving priority queue. Advertiser is billed their clearing price (second-price auction), not their max bid.

**ADV-03 — Spend Transparency**  
As an advertiser, I want a real-time dashboard showing spend, impressions, clicks, and CTR, broken down by day, so I can monitor campaign performance.  
*Acceptance:* Dashboard data lags by no more than 5 minutes from event processing.

**ADV-04 — Brand Safety**  
As an advertiser, I want my ad to only run after it has been reviewed and approved by a human at Ad-Alt, so my brand is never associated with accidental policy violations.  
*Acceptance:* No creative serves impressions until it has a `status: approved` record signed by an Admin user.

### Admin Stories

**ADMIN-01 — Creative Review Queue**  
As an admin, I want a dedicated review interface that shows pending creative submissions with the ad copy, advertiser name, and submission timestamp, so I can approve or reject them efficiently.  
*Acceptance:* Admin can act on a submission in 3 clicks (view, decision, optional rejection reason). Queue is sorted by submission time ascending.

**ADMIN-02 — Fraud Investigation**  
As an admin, I want to view the fraud score breakdown for any developer account or any suspicious event cluster, so I can make an informed decision to pause, reverse, or clear a payout.  
*Acceptance:* Fraud score is displayed as a sum of named components (e.g., `click_velocity: +30`, `account_age: -5`). Every manual override is logged with the admin's identity and reason.

### Finance Stories

**FIN-01 — Ledger Reconciliation**  
As a finance operator, I want to run a period reconciliation that proves total advertiser spend equals total developer earnings plus Ad-Alt fees plus fraud reversals, with zero unaccounted balance.  
*Acceptance:* Reconciliation report shows a zero-balance double-entry summary. Any non-zero balance triggers an automated alert.

**FIN-02 — Payout Disbursement**  
As a finance operator, I want to trigger monthly developer payouts via Stripe, with each developer's payout automatically calculated from their confirmed earnings ledger balance, so disbursements are accurate and auditable.  
*Acceptance:* Payout batch references specific ledger entry IDs. Failed Stripe transfers are logged and retry-queued.

## 7. Non-Goals (MVP and V1)

The following are explicitly out of scope and should not be built unless the product strategy is updated:

1. **Non-VS Code editors** — IntelliJ, Neovim, Emacs, Zed, etc. Future versions only.
2. **Rich media ad units** — images, video, audio, HTML banners. Text-only forever in status bar context.
3. **Programmatic RTB integration** — no DSP/SSP connections, no OpenRTB. Ad-Alt runs its own closed auction.
4. **Direct sales / insertion orders** — no managed campaigns; self-serve only.
5. **Non-developer audiences** — no mobile apps, no websites, no non-IDE surfaces.
6. **Cryptocurrency payouts** — fiat only via Stripe.
7. **Ad targeting beyond broad developer cohort** — no behavioral targeting, no lookalike audiences, no retargeting. Geography and device type only as exclusion criteria.
8. **Sub-publisher network** — Ad-Alt is the only publisher in MVP. No third-party inventory aggregation.
9. **Real-time bidding** — auction is resolved at campaign creation time (reserved impressions) for V1; automated bid optimization is a future feature.
10. **Mobile/tablet VS Code** — desktop VS Code only.

## 8. Privacy Boundaries (Hard Rules)

These are non-negotiable constraints. Any feature proposal that would violate these rules must be rejected at design review, not implementation review.

**PRIV-01:** The extension MUST NEVER transmit the contents of any editor buffer (code, text, or any file content) to Ad-Alt servers or any third party.

**PRIV-02:** The extension MUST NEVER transmit file paths, project names, workspace names, or repository identifiers.

**PRIV-03:** The extension MUST NEVER transmit the text of any AI prompt or AI response.

**PRIV-04:** The extension MUST NEVER transmit the developer's installed extensions list, editor configuration, or operating system details beyond OS family (linux/mac/windows) for fraud scoring.

**PRIV-05:** Ad-Alt MUST publish a machine-readable telemetry schema (JSON Schema) that enumerates every field that can be sent by the extension. This schema must be versioned and the changelog must be public.

**PRIV-06:** Ad-Alt MUST NOT sell, license, or share developer event data with any third party for any purpose other than processing payments (Stripe) and sending required legal notices.

**PRIV-07:** Developer account deletion MUST purge all PII within 30 days. Anonymized aggregate billing records may be retained for accounting compliance.

**PRIV-08:** Ad-Alt MUST comply with GDPR right-of-access and right-to-erasure. Developers in EU/EEA must be presented with a GDPR-compliant consent flow.

**PRIV-09:** IP addresses used for fraud scoring MUST be hashed (not stored in plaintext) after scoring is complete. The hash is retained for deduplication; the raw IP is not.

**PRIV-10:** The extension MUST operate with VS Code's "restricted mode" (workspace trust disabled) without crashing or exposing errors to the developer.

## 9. Abuse Boundaries (Hard Rules)

**ABUSE-01:** Click fraud — Any automated click, programmatic click simulation, or click farm activity that results in inflated click earnings MUST be detected and reversed. The fraud pipeline MUST flag accounts with click rates more than 3 standard deviations above the population mean for human review.

**ABUSE-02:** Impression stuffing — Impression events MUST be tied to a verifiable AI invocation event. Events received without a valid, non-reused invocation token are rejected.

**ABUSE-03:** Sybil accounts — The system MUST maintain a device fingerprint (non-PII) per install to limit impressions per physical device regardless of the number of accounts. Multiple accounts sharing a device reduce the per-account impression cap, not increase total cap.

**ABUSE-04:** Bot installs — The extension MUST require interactive OAuth completion. Headless or CI environments without a display must produce zero billable events.

**ABUSE-05:** Advertiser fraud — Advertisers who submit creative containing malware URLs, deceptive claims, or prohibited content categories (adult, gambling, illicit substances, competitive defamation) MUST be permanently banned. Their active campaigns MUST be terminated with a full refund of unused budget.

**ABUSE-06:** Payout laundering — Developer accounts with no activity for 90 days followed by a sudden spike in impressions MUST trigger a manual review hold before payout. The hold does not affect the developer's earned balance.

## 11. Upgrade Opportunities Over Reference

Ad-Alt is not just a clone with a different name. The following are specific product improvements over what can be publicly observed in the reference product:

1. **Published telemetry schema** — Ad-Alt publishes a versioned JSON Schema for every field sent from the extension. Developers can verify before installing. Reference product has no public schema.

2. **Open-source extension** — Ad-Alt extension is MIT-licensed and auditable. Reference product extension is closed-source.

3. **Explainable fraud scoring** — Every fraud score is a sum of named, weighted signals displayed to the developer. Reference product provides no public explanation of how accounts are evaluated.

4. **Second-price auction** — Ad-Alt runs a Vickrey second-price auction. Advertisers pay the clearing price, not their maximum bid. Reference uses English ascending auction (manual bidding). Second-price encourages truthful bidding without gaming.

5. **Immutable double-entry ledger** — Every financial event is recorded as a debit/credit pair. No event is ever modified; corrections are new entries. Reference product does not publicize its accounting model.

6. **Integer microcents** — All financial calculations use integer arithmetic in microcents (1/1,000,000 of a dollar) to eliminate floating-point rounding errors in earnings splits.

7. **Exact spend/earnings reconciliation report** — Finance operators can run a period reconciliation that proves zero unaccounted balance. Reference does not publish this capability.

8. **Brand-safety creative review SLA** — Ad-Alt commits to a < 4-hour review SLA with a named reviewer on every decision. Reference does not publish a review SLA.

9. **Full GDPR/CCPA data export** — One-click export in JSON and CSV. Reference product's data export capabilities are not publicly documented.

10. **Degraded-mode stability** — If the AI state detection fails for any reason, the extension silently produces zero ads and zero errors. No editor disruption. Reference product's failure modes are not publicly documented.

11. **Per-event earnings ledger visibility** — Every impression and click is individually visible to the developer with amount, timestamp, and advertiser name. Reference shows aggregate earnings.

12. **Stable-API-only extension** — No DOM injection, no monkey-patching, no private API usage. Extension is designed to survive any VS Code update. Reference product's DOM injection approach is observable in the extension manifest.

13. **Device-level deduplication** — Earnings cap per physical device prevents abuse via multiple accounts on the same machine. Reference product's deduplication approach is not documented publicly.

14. **Advertiser budget hard cap** — No advertiser can be charged more than their confirmed campaign budget, enforced at the ledger level, not just the UI level. Reference product's spend cap implementation is not documented.
